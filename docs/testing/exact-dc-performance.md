# 정확 직류 엔진 검증 — 2026-10-02

## 결론

현재 수업 예제의 정확 계산과 2D·3D 자동 조절은 이 데스크톱 환경에서 원활했다. **복잡한 연결망과 큰 분모를 함께 사용하면 동기 계산이 수 초 걸리는 한계는 확인됐다.** 정확성 통과와 모든 입력에서의 실시간 처리 보장을 구분한다. 이번 작업은 검증 도구·결과·후속 항목을 추가했으며 제품 계산 정책과 UI는 변경하지 않았다.

## 검증 계획과 환경

1. 기존 전체 테스트로 계산·저장·측정·표시 경계의 회귀를 확인한다.
2. 일반 fixture와 복잡도·수치 크기를 늘린 회로의 계산 시간을 분리 측정한다.
3. 슬라이더 전 범위의 정확성을 확인하고 반복 갱신 후 메모리를 관찰한다.
4. 배포 빌드에서 2D·3D 자동 조절의 프레임 간격·긴 작업과 실제 측정값을 확인한다.
5. 느린 대표 사례를 CPU 프로파일링하여 다음 개선의 근거를 남긴다.

- Windows, AMD Ryzen 5 5600X, 논리 코어 12개, RAM 약 31.9 GiB, Node 24.18.0.
- 내장 Chromium 154, 표시 영역 1075×1039 CSS px, DPR 1.75. 탭은 측정 내내 표시 상태였다.
- Node 부하 측정, 브라우저 프레임 측정, 전체 테스트는 서로 겹치지 않게 실행했다.
- 대상은 작업 전 커밋 `30915b1` 이후의 정확 엔진 구현 작업본이다. 브라우저는 같은 소스의 기존 최신 프로덕션 빌드를 사용했다. `127.0.0.1:4173` 별도 원점으로 기존 개발 화면의 저장 상태를 보존했다.

## 1. 정확성 및 회귀

- 전체 테스트 **746개 통과**, 42개 파일 통과. Firestore 에뮬레이터 전용 24개는 이번 계산 변경 범위 밖이며 미실행이다.
- 타입 검사, 모듈 경계 검사(110개 소스) 통과.
- 균형 브리지의 중앙 저항·양쪽 도선 0 A, 실제 미세 불균형, 전원 제약·특이성, KCL/KVL·전력·기준점 불변성, 저장 왕복·지원 밖 형식 거부는 기존 정확 연산 테스트를 사용했다.
- FIX-09/11/12 각각 슬라이더 0~1000의 **1001개 값**에서 모든 절점의 KCL과 전체 전력 합이 정확히 0임을 추가 확인했다. 매 회로 10회 전 범위 반복, 총 **30,030회** 해석·전류/전위 모델 생성에 실패가 없었다. 첫 순회의 서로 다른 3,003개 값에 보존식 검사를 수행했다.
- 스트레스 회로도 원래 행렬의 정확 잔차 검사와 전체 절점 KCL·전력 합 검사를 통과했다. 느린 계산을 근사값으로 우회하지 않았다.

## 2. 계산 비용

`solve`는 컴파일된 회로의 해석만 측정한다. `pipeline`은 문서 검증·연결망 생성·해석·진단·모든 도선/부품의 전류 모델·전위 모델 생성을 포함한다. React 렌더링, 저장, GPU 작업은 포함하지 않는다.

준비 실행 3회 후 최대 100회 측정했다. 비용이 큰 사례는 누적 1.5초를 넘으면 최소 8회에서 종료했다. p95는 측정 표본의 95백분위이며, 8회 사례에서는 최댓값과 같다. 별도 계측 실행에서 `rational(n,d)`에 전달된 **약분 전 분자·분모의 최대 비트 수**를 관찰했다. 모든 임시 BigInt와 런타임 내부 메모리의 최댓값을 측정한 것은 아니다.

격자는 인접한 가로·세로 절점을 모두 저항으로 연결하고 대각 모서리 사이에 12 V 전원을 둔다. 일반 값은 101~157 Ω의 소수를 순환 사용한다. 큰 저항비는 각각에 10⁻⁴⁰ 또는 10⁴⁰을 번갈아 곱한다. 긴 분수는 일반 저항값에 `(i+1)/(10^80+7)`을 더한다. 특정 유리수 소거 구현에 불리할 수 있는 수치이며 일반 수업 회로의 대표값으로 취급하지 않는다.

별도 CPU 프로파일의 5×5 큰 저항비 사례에서 `solveCircuit` 아래 표본 3993개 중 **3559개(89.1%)가 gcd**, 409개(10.2%)가 mul에 있었다. 분수 약분과 큰 정수 연산이 주된 병목이다. 프로파일링 실행의 시간은 약 6.25초로, 위의 계측 없는 시간과 섞지 않았다.

## 3. 반복 갱신과 메모리

정확 값 생성 → 해석 → 전류/전위 모델을 10,010회씩 반복했다. 최초 순회와 마지막 순회의 강제 GC 후 힙 차이는 브리지 **−0.387 MiB**, 직렬 **+0.087 MiB**, 병렬 **−0.003 MiB**였다. 힙은 약 22.2~22.7 MiB 범위였고, 반복에 비례하는 증가 경향은 관찰되지 않았다.

별도 스트레스 실행에서는 계산 직후 표본 힙이 시작보다 최대 약 **60.5 MiB** 커졌다. 이는 실제 최대 점유량이나 회로 데이터만의 크기가 아니며, V8의 할당·회수 주기가 포함된 관찰값이다. GPU 메모리, 장시간 브라우저 메모리 누수, 메모리 부족 상황은 이번 검증 대상에 포함하지 않았다.

각 상태에서 1초 준비 후 15초 동안 rAF 간격과 Long Tasks를 관찰했다. 동일 화면의 기준 상태와 비교했으며, 측정 중 뷰포트를 바꾸지 않았다.

## 5. 판단과 남은 위험

- 현재 예제에서 계산 엔진 때문에 갱신 주기를 낮추거나 화면값을 별도로 보간해야 한다는 근거는 없었다.
- 25~49개 절점의 복잡한 회로에서는 계산만으로 한 프레임 예산을 넘는다. 입력값의 분모가 커지면 같은 25개 절점에서도 수 초 동안 메인 스레드를 점유할 수 있다. **큰 입력에 대한 실시간 응답 보장은 미충족**이다.
- 다음 개선은 정확 연산을 유지하며 약분 횟수·분모 팽창을 줄이는 소거 방식의 비교, 결정론적인 연산량/정수 크기 한도와 구조화 실패 처리, 화면과 계산의 실행 분리·취소 가능성 순으로 검토한다. Worker만 도입해도 총 연산 비용이 사라지는 것은 아니다.
- 한 데스크톱의 표본만으로 절점 수·입력 자릿수의 제품 제한을 확정하지 않는다. 연결 형태와 숫자 복잡도가 함께 비용을 결정한다.
- 저사양 교실 기기·모바일·다른 브라우저, 초기 3D 준비 시간, 장시간 UI 메모리, 동시 여러 조절기의 부하는 미확인이다.

## 2026-10-02 과부하 방지 구현 후

계산 명세 §7.6의 `dc-budget-1` 구현을 확인했다. 최초 전체 측정과 30,030회 반복 결과는 [bounded-dc.json](results/2026-10-02-bounded-dc.json), stamp 합산 오차를 포함한 최종 수치 정책과 표시 모델 준비까지 추가한 측정은 [bounded-grid.json](results/2026-10-02-bounded-grid.json)에 보존했다. 이전 측정과 같은 Ryzen 5 5600X / Node 24 환경이며 브라우저 렌더링을 포함하지 않는다.

| 사례 | 이전 정확 풀이 중앙값 | 구현 후 중앙값 | 경로 |
|---|---:|---:|---|
| 일반 25절점 격자 | 29.69ms | 34.07ms | 정확 |
| 일반 49절점 격자 | 303.86ms | 134.29ms | 연산량 예산 후 근사 |
| 큰 분모 25절점 격자 | 6213.88ms | 127.09ms | 정수 크기 예산 후 근사 |
| 큰 저항비 25절점 격자 | 5266.78ms | 160.15ms | 정수 크기 예산 후 수치 불안정 거부 |

연결망 구성·계산·검증·전류/전위 표시 모델 준비를 포함한 pipeline 중앙값/p95는 일반 49절점 142.62/178.61ms, 큰 분모 25절점 99.21/146.91ms, 큰 저항비 25절점 167.66/184.40ms다. 별도 문서/순서와 JIT 실행 상태 때문에 pipeline이 해석 단독 측정보다 짧을 수 있으며 두 시간을 빼서 단계별 비용으로 해석하지 않는다. 가장 극단적인 저항비는 잘못된 근삿값 대신 `APPROXIMATE_SOLVE_FAILED`를 반환했다.

일반 브리지 자동 조절 pipeline p95는 0.88ms였다. 30,030회 반복의 3,003개 서로 다른 슬라이더 위치를 정확 KCL/전력으로 확인했고, GC 후 힙 변화는 브리지 −0.20MiB, 직렬 +0.04MiB, 병렬 +0.08MiB였다. 이 측정은 누수 부재의 증명이나 실제 브라우저 힙/GPU 검증은 아니다.

수치 수용은 bounded-dc 테스트의 알려진 해·정확 해 비교·극단 계수 스케일링·불안정 사례·오차 전파로 확인했다. 전체 751개 테스트 통과, Firestore 에뮬레이터 24개 제외. production build와 114개 소스 파일 모듈 경계 검사도 통과했다. 마지막 정리에서 정확 나눗셈의 불필요한 표시용 변환을 제거하고 근사 파생값의 underflow를 명시적으로 거부했으며 관련 계산·측정 테스트를 다시 실행했다.

한계: 두 예산은 BigInt 정확 경로의 폭주를 제한한다. 문서 파싱, 매우 큰 조밀 행렬의 메모리/근사 LU 비용, 동기 계산으로 인한 프레임 정지를 모두 제한하는 전체 시간 예산은 아니다. 이번 변경에서 실기기 저사양·모바일 및 브라우저 라이브 UI 검증은 수행하지 않았다. 입력 문서에 근삿값을 저장하지 않으며 이전 해를 현재 회로 결과로 재사용하지 않는다.
