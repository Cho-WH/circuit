# 사용 후기와 피드백

요구사항 DAT-005, 결정 [ADR-014](../../decisions/ADR-014-feedback-board.md).

## 현재 구성

`app/FeedbackBoard` → `feedback` 공개 계약 ← `feedback-local`.

앱 상단 한마디 버튼이 네이티브 모달을 연다. 본문 세 줄 미리보기와 더 읽기, 종류, 닉네임, 작성일·수정 여부를 표시한다. 공개 목록과 같은 브라우저의 본인 글을 구분한다. 본인 글에서 닉네임·내용·종류·공개 범위를 수정하거나 삭제할 수 있다. 비밀번호는 받지 않는다. 비공개 작성·수정은 본인 목록으로 이동한다.

수정·삭제는 작성한 브라우저에서만 가능하다는 한 줄 안내와 물음표를 표시한다. 클릭·터치·호버·키보드 초점으로 여는 상세 안내는 사이트 데이터 초기화와 시크릿 모드의 영향, 직접 삭제가 어려울 때 관리자에게 별도 요청하는 방법을 설명한다. Escape는 안내만 닫는다.

현재 연결 지점은 `FeedbackFeature`의 `createBrowserFeedbackPreview()`다. `FeedbackBoard`는 저장소에 직접 접근하지 않는다. 브라우저 익명 ID를 자동 생성하며 `update`·`remove`는 저장된 작성자 ID와 현재 ID를 비교한다. 응답의 `canManage`는 UI 표시용으로 권한 검사를 대신하지 않는다. 수정은 최초 작성 정보와 작성 횟수를 바꾸지 않는다. 삭제는 `deletedAt`만 기록하고 관리자에게 마지막 내용을 보존한다.

로컬 저장 키는 `circuit.feedback.preview.v2`다. 첫 접근 시 버전 1 자료를 순차 이전하여 작성자·작성일·공개 범위·삭제 기록을 유지하고 `updatedAt: null`을 추가한다. 버전 2 자료에서는 비밀번호 salt·해시를 제거한다. 기존 v1 키는 복구용으로 보존하되 이후 읽기·쓰기에 사용하지 않는다. 손상되거나 미래 버전인 v2가 있으면 덮어쓰지 않고 실패한다. 브라우저 데이터 초기화는 익명 ID와 미리보기 글도 지운다. 로컬 ID는 실제 Firebase UID가 아니며 원격 연결 시 기존 로컬 글을 자동 업로드하거나 소유권을 자동 이전하지 않는다.

관리자 UI는 `app/FeedbackAdminPage`와 별도 `/admin/feedback/` 문서다. 일반 게시판에는 관리자 포트나 링크가 없다. 개발 환경에서만 로컬 관리자 포트를 연결하며 운영 빌드는 인증된 관리자 게이트웨이를 연결하기 전까지 기록을 읽지 않는다. 경로 숨김이나 `noindex`는 권한 검사를 대체하지 않는다. GitHub Pages 경로는 `/circuit/admin/feedback/`다.

## Firebase Spark 연결 시 준수할 계약

익명 Authentication과 Cloud Firestore, Security Rules로 구현하며 Cloud Functions를 필수로 두지 않는다. Spark의 서비스별 무료 한도 안에서 운영하는 설계다. Firebase SDK·실제 프로젝트·규칙 배포는 아직 연결하지 않았다.

1. 어댑터가 Firebase 익명 인증과 브라우저 인증 상태 보존을 담당한다. 규칙은 `request.auth.uid`로 작성자 권한을 검사하며 클라이언트가 주장하는 ID·관리자 여부를 신뢰하지 않는다. 관리자 로그인은 게시판 익명 세션을 바꾸지 않도록 별도 Auth 인스턴스 사용을 고려한다.
2. 원문과 공개용 자료를 분리한다. 원문에는 작성자 UID를 보관하고 본인·관리자에게만 읽기를 허용한다. 공개용 자료에는 활성 공개 글의 안전한 필드만 둔다. Firestore 읽기는 필드별 비밀 보장이 아니므로 UID를 공개 문서에 넣지 않는다. 어댑터는 본인 글 ID와 대조하여 `canManage`를 계산한다.
3. 생성·수정·공개 범위 변경·소프트 삭제와 공개 자료 반영은 원자적 쓰기로 처리한다. 규칙의 `getAfter()`로 최종 원문과 공개 자료의 일치를 검증하여 비공개 전환·삭제 후 공개 사본이 남거나 임의 공개 사본이 생성되지 않게 한다. 원문의 물리적 삭제는 허용하지 않는다.
4. 규칙은 허용 필드·자료형·길이·종류·공개 범위를 검사한다. 수정에서는 ID·작성자·최초 작성 시각을 고정하고 수정 시각은 서버 시각과 일치시킨다. 삭제 이후 일반 사용자 변경은 금지한다. UI에서 버튼을 숨기는 것만으로 권한을 보장하지 않는다.
5. 한국 날짜 기준 UID당 하루 3개 제한은 서버 시각과 원자적 쓰기, 보안 규칙으로 강제한다. 예를 들어 날짜·UID별 변경 불가능한 슬롯 3개를 두고 생성 글마다 고유 슬롯 하나를 배정한다. 각 슬롯과 원문이 서로를 가리키며 같은 원자적 쓰기에서 생성됐는지 검사한다. 단순 카운터 증가만 검사하면 한 배치에 여러 글을 끼워 넣을 수 있으므로 이를 허용하지 않는다. 삭제·수정으로 슬롯을 환급하거나 재사용하지 않는다. 클라이언트 날짜는 신뢰하지 않는다.
6. 공개 목록은 활성 공개 자료만, 본인 목록은 인증 UID의 활성 원문만 읽는다. 20개 단위의 안정된 커서를 사용한다. `FeedbackAdminGateway.list`는 검증된 관리자만 전체 원문·수정·삭제 시각을 읽도록 한다. 관리자 허용 목록은 신뢰된 콘솔/관리 도구에서 설정하고 일반 클라이언트의 변경을 금지한다.
7. 인증·네트워크 실패는 `FeedbackResult`로 변환한다. 원격 연결이 완료되면 로컬 미리보기 안내를 실제 상태에 맞게 바꾼다. 다른 브라우저나 초기화된 인증 정보로는 소유권을 복원하지 못한다. 새 익명 UID를 만들 수 있으므로 이 제한은 사람당 제한이 아니다.

실제 연결 단계에서 Emulator로 타인 수정·삭제, 공개 자료 유출, 배치 다중 생성과 동시 요청, 날짜 경계, 관리자 권한을 검증해야 한다. 현재 로컬 저장소는 보안 경계가 아니며 서버 권한·원격 동시성은 아직 검증하지 않았다.

참고: [익명 인증](https://firebase.google.com/docs/auth/web/anonymous-auth), [인증 상태 보존](https://firebase.google.com/docs/auth/web/auth-state-persistence), [보안 규칙 조건](https://firebase.google.com/docs/firestore/security/rules-conditions), [원자적 쓰기](https://firebase.google.com/docs/firestore/manage-data/transactions).
